# Grievances — ledger of non-blocking findings

> Committed register of underlying problems, technical debt and improvements met
> **outside the scope of an in-flight spec**: "what works, but will not scale, or
> only holds together with tape". Committed on purpose — friction should
> accumulate visibly.
>
> **This file is maintained programmatically.** Declare and close entries with the
> `grievances` skill CLI; never hand-edit the index tables below:
>
> ```bash
> grievances.py add --short "..." --severity high --locus "file.go:42" \
>   --finding "..." --impact "..." --fix "..." --effort 0.5d
> grievances.py resolve GRV-0001 --commit 1a2b3c4 --note "..."
> ```
>
> Prose under `# Details` is human-owned and kept verbatim; the heading lines, the
> `<!-- grievance:... -->` markers and both tables belong to the tool, which
> re-sorts them chronologically on every mutation.
>
> **Boundary.** Anything regulatory, security-related, data-losing or needing an
> arbitration does NOT stay here: it becomes a spec, or a fiche in the pilot
> `ROADMAP.md`, immediately — close the grievance with `--promoted-to <ref>` so a
> one-line pointer remains and the analysis lives in exactly one artifact.
>
> Never paste a secret, a token or a credential-bearing log line into an entry:
> record the *command* that retrieves a credential, never its value.
>
> When to read and when to write: `specs/CLAUDE.md`.

### GRV-0002 · medium · 2026-08-19 — reverse-graph targets are never filtered by the context include/exclude patterns

`src/core/impact.ts:205-213` · declared in adversarial review, openai/gpt-5.6-sol, spec 004

<!-- grievance:GRV-0002:prose -->

**Finding.** collectFiles() applies matchesContextPatterns() to importers, but resolveInternalImports() registers every resolved target without it — matchesContextPatterns is reachable only from collectFiles (impact.ts:241). An explicitly excluded file therefore still owns a reverse-graph key and still gets an answer. Importers always come from the filtered set, so an excluded file can never appear AS a dependent; only the queried target is affected. Pre-existing in shape, but the package-widening turns one out-of-scope key per package into N.

**Impact.** A caller who scopes a run with --exclude gets an answer for a file they excluded, so the exclusion does not mean what its name says. Low blast radius today; the ambiguity is what makes it worth recording rather than the damage.

**Fix.** Decide the contract first: either an explicitly named target overrides the exclusion (document it), or filter targets in resolveInternalImports. **Effort: 2h.**

### GRV-doctor-never-report-missing-14fd · medium · 2026-09-15 — doctor can never report a missing runtime: both availability flags are constants

`src/cli/doctor.ts:76` · declared in adversarial review of the docs freshness pass, 2026-09-15

<!-- grievance:GRV-doctor-never-report-missing-14fd:prose -->

**Finding.** buildDoctorReport() sets node.available to the literal true, and derives spaghettiCompass.available from !!spaghettiCompassPath where the path comes from path.resolve(__dirname, '../../bin/spaghetti-compass.js'). path.resolve never throws on a missing file, so the catch branch that would fall back to a PATH lookup is unreachable and both flags are always true. getDoctorExitCode() therefore always returns 0. Proven: deleting bin/spaghetti-compass.js and running dist/cli/index.js doctor in a container still prints 'OK spaghetti-compass /app/bin/spaghetti-compass.js' and exits 0.

**Impact.** The doctor exit code carries no information, so no script or agent can branch on it, and the two runtime rows cannot report the failure they exist to report. Documentation that describes the intended semantics is forced to describe the defect instead.

**Fix.** Replace the path.resolve assignment with an fs.existsSync check on the resolved bin path, falling back to checkTool('spaghetti-compass'); derive node.available from the resolved node path rather than a literal. **Effort: 0.5d.**

### GRV-tsconfig-commander-stores-ce74 · medium · 2026-09-15 — --no-tsconfig is a no-op: Commander stores the negation under the positive key

`src/cli/index.ts:158` · declared in adversarial review of the docs freshness pass, 2026-09-15

<!-- grievance:GRV-tsconfig-commander-stores-ce74:prose -->

**Finding.** Both commands declare .option('--no-tsconfig', ...) and then branch on options.noTsconfig — explore with 'if (options.noTsconfig)', impact with 'if (!options.noTsconfig)'. Commander stores a negated option under its POSITIVE key: --no-tsconfig sets options.tsconfig = false and never defines options.noTsconfig. Both branches therefore read undefined, and both fall through to TsConfigResolver.findTsConfig() auto-discovery. Proven on a fixture with a paths alias '@app/*': 'explore src/main.ts -c src --json' and the same command plus --no-tsconfig both resolve the alias, 4 matches each. Note --no-transitive and --no-links are handled correctly elsewhere in the same file (options.transitive !== false, options.links === false), so the defect is local to this flag.

**Impact.** A caller who disables alias resolution to reproduce a resolver bug, or to analyze a project whose tsconfig is wrong, silently gets the opposite of what they asked for. The flag is documented on both commands and cannot be worked around except by moving the tsconfig.

**Fix.** Branch on options.tsconfig === false instead of options.noTsconfig, in both the explore and impact actions. **Effort: 0.5d.**
